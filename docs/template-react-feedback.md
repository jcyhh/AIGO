# template-react 实战反馈

## 用途

本项目同时承担 `template-react` 的实战验证任务。在实际业务开发中发现适合复用到模板的规范、能力、缺陷修复或体验优化时，统一记录在本文档中，暂不因为模板演进阻塞当前项目。

模板仓库：<https://github.com/jcyhh/template-react.git>

## 记录原则

- 只记录具有通用价值、适合多个 React 项目复用的内容。
- 当前项目特有的业务需求不回灌模板。
- 每条建议必须包含实战场景、发现的问题、建议方案和验证结果。
- 优先记录事实和复现方式，避免只有结论没有依据。
- 模板更新由用户集中安排；未经确认，不直接修改模板仓库。
- 当前业务开发优先，不因等待模板更新而暂停。

## 状态说明

- `待评估`：已从实战发现，尚未决定是否回灌。
- `计划回灌`：已确认适合模板，等待模板维护任务处理。
- `已回灌`：已在模板仓库完成。
- `不回灌`：确认只适用于当前项目或收益不足。

## 反馈清单

### TRF-001：复制模板后缺少本地环境文件

- 状态：待评估
- 实战场景：从模板仓库复制代码到一个全新的业务项目后安装依赖并运行测试。
- 发现的问题：`.env.development` 和 `.env.production` 按约定不被 Git 跟踪，因此新项目首次运行时不存在；环境变量约定测试会因文件缺失而失败，构建时也会提示 `VITE_APP_NAME` 未定义。
- 建议方案：在模板 README 的初始化步骤中明确要求基于 `.env.example` 创建两份本地环境文件；也可以提供一个 pnpm 初始化脚本完成复制，但不得覆盖已经存在的环境文件。
- 当前项目处理：已创建 `.env.development` 和 `.env.production`，字段与 `.env.example` 一致。
- 验证结果：`tests/env-convention.test.mjs` 的 3 项测试全部通过，两份实际环境文件均被 `.gitignore` 忽略。

### TRF-002：全新复制后缺少 VS Code 工作区设置

- 状态：计划回灌
- 实战场景：从模板仓库复制代码后直接运行完整测试。
- 发现的问题：`tests/vscode-settings.test.mjs` 强制要求 `.vscode/settings.json` 存在且内容完全符合预设，但该配置只服务 VS Code 或兼容编辑器，不影响项目运行、构建和业务行为。未使用 VS Code 的开发者不需要该文件；同时 `.gitignore` 默认忽略 `.vscode/*`，只放行了 `extensions.json`，导致全新复制后完整测试失败。模板测试把可选的编辑器偏好错误地当成了项目必需契约，约束过严。
- 建议方案：删除测试中对 `.vscode/settings.json` 存在性和具体内容的强制校验。可以继续将该文件作为可选的开箱体验提交到模板，并在 `.gitignore` 中明确放行；也可以只在 README 中提供配置示例。无论采用哪种方式，编辑器配置都不应阻塞项目测试。
- 当前项目处理：已从模板复制 `.vscode/settings.json`，当前 VS Code 用户可以获得 SCSS 类名补全；该文件仍被 Git 忽略。
- 验证结果：文件存在时对应测试通过，但这只能证明编辑器配置符合测试预设，不能证明任何运行时、构建或业务行为，因此该测试不属于必要的项目质量门禁。

### TRF-003：新项目缺少明确的初始化入口和配置清单

- 状态：计划回灌
- 实战场景：开发者从模板复制出一个全新项目，准备开始实际业务开发。
- 发现的问题：模板包含较多 README、模块说明和配置能力，但没有一个面向“新项目第一次启动”的明确入口。更关键的是，现有注释大多只说明配置值是什么，没有形成可交接的决策说明：接手者不知道为什么要配置、什么业务场景应该选哪个值、默认值是否可以直接用于正式项目、配置错误会影响哪些模块，以及哪些值在页面开发期可以留空。模板作者可以依靠开发背景补全这些信息，其他开发者无法可靠判断。信息虽然存在于不同文件中，但缺少按执行顺序组织的初始化流程和配置决策契约。
- 建议方案：在模板顶层 README 增加醒目的“新项目初始化”入口，并提供一份可交接的配置表。每一项至少说明：配置位置、用途、可选值、模板默认值、选择依据、修改阶段、是否必填、留空行为、影响范围和验证方式。至少覆盖项目名称与包信息、`.env.development`/`.env.production`、API 地址、部署路径、首页路由、登录模式、布局模式、DApp 链与合约配置、语言开关、品牌资源和最终验证命令。初始化清单按“立即必改、按项目确认、对接接口时、上线前”分阶段，不能只罗列文件名。可进一步提供只做检查、不覆盖已有值的 `pnpm setup:check`，明确报告仍在使用模板默认值或尚未确认的配置，但不把项目特有值写死在模板中。
- 确定方案：采用 Markdown 驱动的 AI 初始化问卷，不开发交互式脚本。模板新增 `PROJECT_SETUP.md` 定义问题、简短选项说明、是否允许跳过、回填位置和验证方式；`AGENTS.md` 要求 AI 在新项目开发前检查并执行该问卷。AI 一次询问一个配置项，只解释模板语义，不进行技术入门教学、不推荐选项，也不替开发者作决定。所有当前阶段必需配置必须由开发者明确回答，即使答案与模板默认值相同也不能自动确认。API、RPC、合约地址等阶段性配置允许明确选择“跳过”，并记录应补齐的开发阶段。全部回答完成后，AI 先展示汇总，由开发者确认，再统一回填项目配置并验证。
- 固定约束告知：问卷开头应先列出不可选择的项目约束，并要求开发者确认已知晓。包管理器固定使用 pnpm，依赖安装、开发、测试、构建和 lint 都通过 pnpm 执行；不得使用 npm 或 yarn，也不得生成 `package-lock.json` 或 `yarn.lock`。这不是问卷选项，AI 不询问是否改用其他包管理器。现有 `preinstall` 拦截继续保留，用于误操作时快速失败，但不能替代项目初期的主动告知。
- 品牌资源必改项：新项目初始化必须要求开发者提供并替换项目 Logo，不能继续使用模板占位 Logo。Logo 统一使用 PNG 资源并放在 `public/brand/app-logo.png`，公共品牌组件和默认开屏页共用这一份资源；开屏页项目名使用 `APP_CONFIG.name` 文本渲染，不单独制作带项目名的开屏 Logo。问卷需要明确检查文件已替换；如果尚未取得正式资源，可以标记为待补，但初始化状态必须保持未完成或明确列为上线前必改项。
- 初始化状态：问卷完成后生成可提交 Git 的 `PROJECT_SETUP_STATUS.md`。该文件只记录已确认项和待配置项，不写冗长决策过程。已确认项用于区分“项目明确采用该值”和“仍在使用未确认的模板默认值”；待配置项记录跳过内容及应补齐阶段。
- 多语言问卷边界：初始化阶段只确认项目是否启用多语言，不要求立即确定最终语言清单。模板和新项目默认只启用肯定存在的三种语言：简体中文 `zh-Hans`、繁体中文 `zh-Hant` 和英语 `en`。其他语言资源可以继续由模板保留，但不默认加入 `APP_LANGUAGES`；待产品明确目标语言后再按需启用。默认语言不纳入问卷，统一沿用模板规则：开发环境使用简体中文，方便开发；生产环境使用英语，适应常见上线用户群。该规则属于模板明确约定，不需要每个项目重复决策。
- 当前项目处理：由开发协作过程逐项识别并修改，尚无统一的新项目初始化清单。
- 验证结果：本项目首次复制后，开发者无法仅凭顶层入口判断应先创建 env、设置应用名、接口地址及其他公共配置，说明当前文档的信息架构不足以支持顺畅开工。

### TRF-004：公共品牌 Logo 样式不应假设图片为正方形

- 状态：计划回灌
- 实战场景：在项目中用真实品牌 Logo 替换模板占位资源。
- 发现的问题：品牌 Logo 的宽高比例由实际资源决定，不一定是正方形。如果公共品牌组件同时固定宽度和高度，非正方形 Logo 会被拉伸、压缩或裁切，不符合可替换模板资源的设计目标。
- 建议方案：公共 `AppBrand` Logo 默认固定展示宽度并使用 `height: auto` 保持图片原始比例。需要严格限制布局高度时优先使用 `max-height` 和 `object-fit: contain`，不要默认强制正方形尺寸。页面特有尺寸由调用方或项目样式调整。
- 当前项目处理：`AppBrand.scss` 已由开发者调整为 `width: 40px; height: auto;`。
- 验证结果：该写法可以兼容横向、纵向和正方形 Logo，替换资源时无需同步修改固定高度。

### TRF-005：语言配置测试不应锁死项目启用的完整语言清单

- 状态：计划回灌
- 实战场景：新项目根据产品需求增减启用语言。
- 发现的问题：当前 `tests/i18n-config.test.mjs` 把 14 种启用语言及顺序写死。语言范围本质上是项目配置，产品后续增减语言会迫使开发者同步修改模板契约测试，容易把可变配置误判为功能回归。
- 建议方案：测试稳定的多语言模块契约，例如启用语言使用标准 code、每个启用语言能加载公共资源、默认和回退语言存在于启用列表。不硬编码完整语言数量、具体清单和人工维护顺序。模板初始配置仅启用 `zh-Hans`、`zh-Hant`、`en`，其他语言由项目按产品要求增加。
- 当前项目处理：已确认 AIGO 初始只需要简体中文、繁体中文和英语；当前代码仍保留模板原有 14 种启用配置，等待当前项目配置调整时一并修改。
- 验证结果：现有测试可以验证所有当前启用语言具有欢迎文案，但首项测试同时把业务可变语言列表锁死，超出了稳定模块契约范围。

### TRF-006：开发服务器应默认提供局域网访问地址

- 状态：计划回灌
- 实战场景：前端启动静态页面或联调环境后，需要由同一局域网内的后端、测试人员和移动设备访问项目。
- 发现的问题：当前 `pnpm dev` 仅执行 `vite`，开发服务器默认只绑定本机地址。终端只显示 Local 地址，并提示使用 `--host` 才能暴露 Network 地址，其他设备无法直接访问，增加联调和测试沟通成本。
- 建议方案：模板开发命令默认启用 Vite 的局域网监听，例如将 `dev` 设置为 `vite --host 0.0.0.0`，或在 `vite.config.ts` 的开发服务器配置中设置 `server.host`。启动后终端应同时显示 Local 和 Network 地址。该设置只用于开发服务器，不影响生产构建和部署；文档应提醒开发者仅在可信局域网中使用。
- 当前项目处理：尚未修改，当前启动命令仍只提供 Local 地址。
- 验证结果：运行 `pnpm dev` 时 Vite 显示 `Network: use --host to expose`，可以稳定复现。

### TRF-007：项目环境地址统一通过本地 env 配置

- 状态：计划回灌
- 实战场景：开发和部署 DApp/H5 项目时，需要配置公司内部 API 地址、RPC 地址、合约地址以及客户提供的生产参数。
- 发现的问题：如果把公司内部 IP、开发接口地址、RPC 地址等直接写在源码中，它们会随代码提交到 Git，造成环境耦合，也可能在公开仓库中暴露项目内部配置。
- 建议方案：类似 `VITE_BASE_URL`、`VITE_RPC_URL`、`VITE_USDT` 的项目和环境相关值统一放在 `.env.development`、`.env.production` 中，不在业务代码里硬编码；两份实际 env 文件继续保持不被 Git 跟踪，仓库只提交空值和说明完整的 `.env.example`。后续发现新的环境相关地址或项目参数时，优先评估是否应增加 env 配置。
- 必要边界：该设计主要用于环境隔离和避免配置进入 Git，不代表 `VITE_*` 值对浏览器保密；前端运行必需的值在构建后仍属于客户端可见信息。前端项目不存放私钥等真正秘密。
- 当前项目处理：`VITE_BASE_URL`、`VITE_RPC_URL` 和 `VITE_USDT` 保持为空，待对应开发阶段填写。

### TRF-008：项目品牌统一使用 public/brand 下的单一 PNG Logo

- 状态：计划回灌
- 实战场景：新项目替换模板品牌 Logo，并在 Header、Sidebar 等公共品牌区域复用。
- 发现的问题：品牌 Logo 通过类似 `@/assets/layout/headbar/logo.png`、`@/assets/start/splash-logo.png` 的页面深层路径分别维护，替换入口不直观，并产生内容重复的 Header Logo 和开屏 Logo。默认开屏实际只需要“项目 Logo + 居中项目名”，无需维护第二张包含文字的合成图片。
- 约束方案：模板项目 Logo 必须使用 PNG，统一放在 `public/brand/app-logo.png`。公共 `AppBrand` 和默认 `SplashPage` 通过部署路径感知的 public URL 共用该资源；开屏项目名直接渲染 `APP_CONFIG.name`。普通页面业务图片仍放在 `src/assets/<页面语义目录>/`，`public/brand` 只存放初始化必须替换的品牌资源。Logo 引用必须兼容 `/h5/` 等非根目录部署。模板回灌后必须删除旧 `src/assets/layout/headbar/logo.png`、`logo.svg` 和 `src/assets/start/splash-logo.png`，不得保留重复品牌资源。
- 初始化要求：替换 `public/brand/app-logo.png` 是新项目初始化的必做项。AI 问卷需要明确要求开发者提供项目 Logo，并检查 Header、Sidebar 和默认开屏页均引用同一文件。Logo 展示继续遵循固定宽度、`height: auto` 的比例适配规则；`public/favicon.ico` 仍作为另一项品牌资源单独替换。
- 当前项目处理：AIGO 已迁移为 `public/brand/app-logo.png`，`AppBrand` 与 `SplashPage` 共用；开屏页在 Logo 下方显示 `APP_CONFIG.name`。旧 Header PNG/SVG、旧开屏 Logo 及空的 `src/assets/start` 目录已删除。当前 PNG 等待开发者替换为最终 AIGO Logo。
- 验证结果：相关组件和开屏页测试 8 项通过，生产构建和 lint 通过；构建产物只保留一份 public 品牌 Logo，不再生成旧开屏 Logo chunk。

### TRF-009：Vite base 必须与应用部署路径保持一致

- 状态：计划回灌
- 实战场景：应用路由部署在 `/h5/`，并从 `public` 使用项目 Logo 等静态资源。
- 发现的问题：模板的 `APP_CONFIG.routeBase` 和 React Router basename 已设置为 `/h5/`，但 `vite.config.ts` 未配置 `base`，Vite 仍按 `/` 处理开发和构建资源路径。首次迁移 `public/app-logo.png` 后，开发服务器请求 `/h5/app-logo.png` 返回 SPA HTML，而不是 PNG，暴露了配置不一致。
- 建议方案：Vite `base`、应用 `routeBase` 和 Router basename 必须来源一致，至少在模板默认值上统一为 `/h5/`。后续初始化问卷修改部署路径时，AI 必须同步更新并验证三处配置，避免路由可用但静态资源失效。
- 当前项目处理：AIGO 已在 `vite.config.ts` 设置 `base: '/h5/'`，与现有应用和路由配置保持一致。
- 验证结果：修改前 `/h5/app-logo.png` 返回 `text/html`；修改后返回 HTTP 200 和 `Content-Type: image/png`，开发服务器显示的 Local、Network 地址也统一带 `/h5/`。

### TRF-010：未配置开发接口时允许 DApp 签名使用临时登录态

- 状态：计划回灌
- 实战场景：项目处于静态页面开发阶段，尚未提供登录接口，但需要完成钱包连接、签名、进入首页以及后续页面流程。
- 发现的问题：DApp 登录签名后必须等待地址登录接口返回 Token，未配置开发接口时无法建立本地登录态并进入首页。临时直接删除认证流程又会偏离真实的钱包交互路径。
- 规范方案：钱包连接和签名流程保持真实执行。仅当运行于开发环境且 `VITE_BASE_URL` 为空时，签名成功后跳过登录请求并调用 `completeLogin('token')`，用于静态页面开发。开发环境一旦配置 `VITE_BASE_URL`，立即恢复正常地址登录接口请求。
- 生产边界：生产环境始终请求登录接口，不使用临时 Token。`.env.production` 的 `VITE_BASE_URL` 强制保持为空，Axios 使用相对 `/api/...` 地址请求当前网站同源接口；不能填写正式接口域名，也不能把“生产地址为空”误判为“接口尚未接入”。初始化问卷应把它作为固定约束告知，而不是可填写配置项。
- RPC 生产边界：`.env.production` 的 `VITE_RPC_URL` 同样强制保持为空。该变量只配置开发环境的 `DAPP_LOCAL_CHAIN` RPC；生产环境直接使用 `DAPP_PRODUCTION_CHAIN`，不读取此配置。初始化问卷只允许在开发联调阶段询问本地 RPC 地址，不应提供生产 RPC 填写项。
- 当前项目处理：AIGO 已在认证配置中集中判断该规则，DApp 登录流程根据环境和 `VITE_BASE_URL` 自动选择临时登录态或真实接口，无需在对接阶段手动改回代码。
- 验证结果：相关认证测试需覆盖临时分支仅由 `DEV && !VITE_BASE_URL` 触发，同时保留真实 `requestDappLogin()` 和接口返回 Token 的完成流程。

### TRF-011：用 Stylelint 强制禁止重复全局工具样式

- 状态：计划回灌
- 实战场景：页面开发时，全局 SCSS 已生成间距、字号、字重、行高、透明度和动画时长等工具类，但开发者仍可能在页面 SCSS 中重复声明相同具体值，使工具类体系失去约束力。

### TRF-012：禁止 TSX inline style 绕过 PostCSS 自适应

- 发现的问题：当前首页实战中，部分应依赖设计切图或真实图标的区域被临时代码样式应付。即使布局大体可用，细节还原度会明显下降，并且后续人工返工成本高。
- 建议方案：模板新增页面开发前置流程：开发设计稿页面前，先由开发者或设计协作方人工从 Figma 导出页面所需 PNG/SVG/WebP 切图，并放入项目语义化资源目录。AI 开始写页面前必须先检查资源清单和设计稿结构；复杂图片、装饰边框、光效、页面背景、图片型按钮和非常规图标优先使用切图。缺少必需资源时，AI 应暂停实现并列出缺失资源名和建议路径，不得擅自用 CSS、文字、emoji 或临时符号替代。只有纯色、渐变、圆角、普通边框、常规布局和可复用基础组件才默认用代码实现。
- 可访问性边界：装饰性设计切图不强制要求编写 `alt`，后续页面开发不把视觉切图缺少 `alt` 当作阻塞问题；真正承载业务信息或交互含义的图片再按具体场景补语义。
- 资源路径约定：页面专属资源放在 `src/assets/<page-name>/`，按语义命名，例如 `home-bg.png`、`home-card-frame.png`、`token-usdt.svg`。品牌初始化资源继续放在 `public/brand/`，不与页面切图混放。
- 当前项目处理：已将该规则写入 `AGENTS.md`，后续开发新页面前先确认切图资源是否齐全。当前已写出的首页若继续精修，应优先补齐真实设计切图，再替换临时代码图形。
- 验证结果：本次为流程和文档规范更新，后续页面开发时通过人工资源清单、页面实现检查和构建门禁共同验证。

### TRF-024：Figma 页面生成必须先做实现清单再写代码

- 状态：计划回灌
- 实战场景：开发者直接提供 Figma 链接并希望 AI 生成页面时，AI 容易只按视觉结果“摹写”页面，而没有先对齐项目已有封装、控件语义和切图边界。当前首页实战中出现了两个典型问题：本应是输入框的区域先被写成静态 `div`，本应复用 `full-btn` 或 `@include full-button(...)` 的确认按钮被写成了页面私有按钮结构。
- 发现的问题：Figma 设计稿主要表达视觉结构，不会自动告诉 AI 当前项目已经有哪些全局组件、mixin、工具类和封装边界。仅靠 `AGENTS.md` 中“优先复用公共类”的原则仍不够，AI 在页面生成时可能跳过“查已有封装”这一步，导致重复 SCSS、错误语义元素和后续接接口成本增加。
- 建议方案：模板新增强制页面生成前置流程。AI 收到 Figma 链接后，不能直接写页面代码，必须先检查设计稿和项目现状，并输出一份实现清单供开发者确认。清单至少包含：所需切图资源、语义化 UI 元素、可复用组件、可复用样式类、可复用 mixin、页面专属例外和待确认项。AI 在写页面 SCSS 前必须检查 `src/components`、`src/styles`、`src/styles/mixins.scss`、showcase 页面和相近页面实现。
- 按钮约束：通栏主操作按钮默认使用 `full-btn` 或 `@include full-button(...)`；内容自适应按钮默认使用 `auto-btn` 或 `@include auto-button(...)`。只有设计明确需要共享按钮结构无法表达的形状、图片背景或交互时，才允许写页面专属按钮结构，并应在实现清单中说明原因。
- 语义约束：视觉控件写样式前先判定语义。输入区域必须使用 `input` 或 `textarea`，操作使用 `button`，跳转使用路由/导航封装，进度展示优先使用公共进度组件。不得为了静态页面方便把交互控件写成普通 `div`。
- 当前项目处理：已将该流程写入 `AGENTS.md`，并新增文档契约测试，要求 Figma 页面实现流程、按钮复用和语义元素规则继续存在。首页后续精修时应按该流程重新核对确认按钮、输入框、进度条和切图资源。
- 验证结果：本次为规范和反馈记录更新，后续页面实现通过页面前置清单、文档契约测试、lint、测试和构建门禁共同验证。

### TRF-025：静态页面也要实现基础本地交互

- 状态：计划回灌
- 实战场景：项目处于静态页面开发阶段，接口尚未接入，但页面设计稿已经包含 tab、输入框、按钮、弹窗、复制等可交互控件。
- 发现的问题：把“静态页面”理解成“无交互截图”会导致 tab 只画出两个按钮却不能切换，输入区域被写成静态文本，弹窗和展开收起没有最小状态流。这样第一版虽然能看，但后续接接口时还要重写结构和状态，返工成本高。
- 建议方案：静态数据不等于无交互截图。页面开发期可以不请求接口、不接合约，但设计中明确出现的基础本地交互应先用本地 state 和静态数据实现，例如 tab 切换、输入框、展开收起、弹窗开关、复制按钮、领取按钮禁用态等。交互只需要走到前端状态层，不需要提前模拟复杂业务链路。
- 当前项目处理：AIGO 首页协作订单 tab 已改为本地状态切换，并按订单状态过滤静态数据；订单进度区顺序同步按设计调整。
- 验证结果：新增首页结构测试和文档契约测试，要求后续页面保留基础本地交互的实现习惯。

### TRF-026：重复出现的居中弹窗卡片皮肤应沉淀为 Popup 内容主题

- 状态：计划回灌
- 实战场景：存钱罐页面的存入和提取弹窗使用同一类居中卡片视觉：模糊遮罩、渐变背景卡片、渐变边框、顶部标题和右上角关闭按钮。
- 发现的问题：如果每个页面都通过 `contentClassName` 私写完整卡片外壳，会让 Popup 公共封装只剩遮罩能力，后续相同弹窗视觉在购买、确认、领取等场景里反复复制。
- 建议方案：Popup 的预设内容外壳保留默认主题，同时增加 `contentTheme` 这类语义化视觉主题参数。初始至少支持 `default` 和 `gradient-card`，其中 `gradient-card` 复用模板已有 `gradient-card` mixin，颜色和渐变走全局变量配置。页面只写表单、按钮、余额等业务主体，不重复写公共卡片边框与背景。
- 当前项目处理：AIGO 已给 `PopupContentCenter` 和 `PopupContentBottom` 接入 `contentTheme`，并新增 `gradient-card` 公共样式；存钱罐存入/提取弹窗使用该主题。
- 验证结果：新增 Popup 内容主题契约测试，要求主题类型、主题 class、渐变卡片样式和全局变量持续存在。

### TRF-027：项目术语必须形成统一词表并可被测试约束

- 状态：计划回灌
- 实战场景：Figma 节点、历史项目习惯和业务口头描述可能对同一动作使用不同词，例如 Token 取回动作同时出现“提取”和“提现”。
- 发现的问题：如果 AI 完全照搬设计稿文字，页面不同位置会出现不一致文案，后续多语言、接口字段、测试用例和运营口径都会被拖乱。
- 建议方案：项目初始化和页面开发阶段都应维护一份业务术语约束。设计稿与术语表冲突时，源码以术语表为准，并把差异记录到实现说明或反馈文档。对关键禁用词可以增加轻量测试扫描一方 UI 源码，防止后续误写。
- 当前项目处理：AIGO 已确认 Token 取回动作统一叫“提取”，不叫“提现”；`AGENTS.md` 已写入术语规则，并新增源码扫描测试。
- 验证结果：新增术语测试扫描 `src` 下的一方 UI 源码，出现“提现”会直接失败。

### TRF-028：页面内分段 Tab 应沉淀为公共 SegmentedTabs 组件

- 状态：计划回灌
- 实战场景：AIGO 首页“协作订单”的“进行中 / 已完成”切换已经实现了基础本地交互，并按当前选中项过滤静态数据。该控件包含容器背景、绝对定位选中色块、选中色块位置动画、文案颜色过渡和多个按钮项，后续订单、资产、流水、收益明细等页面都可能重复出现。
- 发现的问题：如果每个页面都私写同样的 tab 结构，容易重复写动态选中类、动画色块和 `aria-pressed`，也容易出现有的页面只改背景色、没有滑块动画，交互体验不统一。
- 建议方案：模板新增公共 `SegmentedTabs` 或 `TabSwitch` 组件，采用受控模式：`options`、`value`、`onChange`。组件内部负责按钮语义、选中态、禁用态、选中色块动画和文案颜色过渡。因为项目禁止 TSX inline style，选中色块位置不能用 `style={{ left }}`，应通过 `count` 和 `activeIndex` 修饰类控制，默认支持常见的 2 到 5 项。颜色、背景、圆角、高度、内边距和选中色块背景走全局变量或组件 class 扩展。
- 边界约束：该组件只负责“同级互斥筛选 / 状态切换”，不负责请求分页、列表过滤业务或路由跳转。页面继续自己维护状态和数据过滤；如果是一级菜单或路由导航，应继续使用路由/菜单封装，不用该组件。
- 当前项目处理：AIGO 首页当前仍是页面私有实现，已经证明需要抽公共组件；下一步可以先抽 `SegmentedTabs` 并替换首页订单 tab。
- 验证结果：本次先记录模板反馈，后续实现组件时需补组件契约测试，覆盖受控值、点击回调、选中态 class、无 inline style 和首页接入。

### TRF-029：模板缺少分页组件，接口阶段前应补基础 Pagination

- 状态：计划回灌
- 实战场景：AIGO 当前静态页面已有多个列表：协作订单、闪兑记录、流水明细。现在用静态数组直接渲染，接口阶段接入真实列表后必然需要页码、上一页/下一页、加载状态、空状态和列表刷新策略。
- 发现的问题：模板目前没有公共分页组件。若接口阶段每个页面自己处理分页按钮和边界值，容易出现页码越界、重复请求、禁用态不统一、移动端分页样式不一致。
- 建议方案：模板新增受控 `Pagination` 组件，基础参数包括 `currentPage`、`pageSize`、`total` 或 `totalPages`、`onChange`、`disabled`。默认提供上一页、下一页、页码项和省略号展示，内部负责页码边界裁剪与按钮禁用态。移动端 H5 也应预留 `simple` 或 `load-more` 轻量展示模式，但不要把接口请求、列表数据和滚动加载写进组件内部。
- 边界约束：分页组件只负责展示和发出页码变化，页面或 feature service 负责请求接口、维护 loading、合并列表和错误处理。若项目设计最终采用触底加载或“加载更多”，可以复用同一分页状态模型，但 UI 变体应和页码式分页区分。
- 当前项目处理：AIGO 仍处于静态页面阶段，暂不强行把当前静态列表改成分页；先记录为接口阶段前的公共能力缺口。
- 验证结果：本次先记录模板反馈，后续实现时需补页码计算测试、边界禁用测试、无 inline style 测试和 showcase 示例。

### TRF-030：静态页收尾后应做一次公共视觉原语复盘

- 状态：计划回灌
- 实战场景：AIGO 静态页完成后，多个视觉结构开始重复出现：带左右渐隐线的区块标题、Token 胶囊、金额输入框加“全部”、渐变/半透明记录卡片、列表行分隔线等。
- 发现的问题：这些结构如果在第一个页面就过早抽象，容易把项目专属样式误判成模板能力；但如果完全不复盘，后续页面会继续复制相同 SCSS，公共组件体系也会错过真实项目打磨出来的高频结构。
- 建议方案：每完成一轮静态页面，应做一次“公共视觉原语复盘”。规则是：两个以上无关页面稳定重复、语义一致、业务逻辑轻、样式可通过变量配置时，优先抽公共组件或公共样式；只出现在单页、依赖具体切图、依赖业务字段或只是视觉相似但语义不同的结构，先保留在页面内。
- 当前候选：`SectionTitle` 适合承载左右渐隐线标题；`TokenPill` 适合承载图标 + Token 名称胶囊；金额输入 + 余额 + 全部更适合等接口阶段确认资产选择、精度、最大值规则后再抽；记录卡片先保留页面内，因为 home、swap、weight 的信息结构差异较大。
- 当前项目处理：AIGO 暂不批量抽所有候选，优先考虑先抽首页订单 tab 为公共 `SegmentedTabs`，分页组件作为接口阶段前置能力。
- 验证结果：本次先记录模板反馈，后续每抽一个公共组件都应补 README、showcase 和契约测试。
